# Solana order transactions

FESOL-56 provides a lazy Solana adapter for shared order-entry and order-editor consumers (FESOL-19). The application and GMX SDK keep their existing USD/token units; `orderInputs.ts` converts them using the FESOL-92 helpers. It does not add another trading page.

## Supported contract

The builder uses GMX-built `@gmsol-labs/gmsol-sdk@0.11.0-beta.1` from `vendor/gmsol-sdk`, with the WASM hash pinned in `config/gmsol/sdk.ts`. The instruction subset in `orderAbi.json` has matching discriminators and account order in `crates/programs/idls/gmsol_store.json` at the pinned source commit `7fe4008292ffc09061f3a733ad9b5cd2e6235fa8`. See `vendor/gmsol-sdk/BUILD.md` for build provenance. Live deployment compatibility still requires simulation and acceptance; a matching package API is not deployment evidence.

Supported actions are direct market/limit increases, market decreases, take-profit/stop-loss decreases, updates of position orders and cancellations of any order kind, swaps included. Preparation of the wallet user and associated token accounts is idempotent. Only an increase prepares its position, so a decrease whose position is already gone fails simulation instead of re-creating an empty position. Native SOL payments explicitly wrap only the intended amount into the wallet's WSOL account and set the increase's unwrap flag, so a cancelled order refunds SOL rather than WSOL; its TP/SL keep the flag off. Owner, fee payer, receiver and rent receiver must be the connected wallet. Callback orders, swap routes and Token-2022 account setup are rejected until their account ABI is reviewed.

A standalone create has one order. An atomic action starts with one market increase and contains at most one TP and one SL for the same position, each no larger than the existing position plus the increase; the program caps a trigger decrease at the position size if the increase never fills. A limit increase takes no TP/SL, because a trigger that fires before the limit fills fails on the empty prepared position and the keeper's soft failure closes the position account the limit order needs. A WASM transaction group is **not** atomic: the adapter keeps all orders and escrow setup in one version-0 transaction, moving wallet-account preparation into an earlier transaction when necessary. If the final order transaction still exceeds the packet limit, construction fails before signing. The packet limit is 1232 bytes; compute units are capped at 1,400,000. Nonatomic preparation/actions execute serially, with at most four transactions total. All transactions are built with one fresh blockhash. Once a group confirms, the sender fetches a new blockhash for the remaining groups and replaces only that field, after checking that the rest of each message is byte for byte the same, so their nonces and order accounts do not change; the validator accepts exactly one blockhash per group. A transaction whose blockhash expires before the wallet prompt requires rebuilding and signing again. If it expires while the prompt is open, nothing has been broadcast or recorded yet, so the sender refreshes the blockhash of that group and of the later groups in the same way, reruns the pre-signature checks and asks the wallet once more. Later groups are refreshed too because the pre-signature check estimates their fees, and `getFeeForMessage` returns nothing for an expired blockhash. A second expiry requires rebuilding and signing again.

An atomic native-SOL increase first spends the wallet's existing WSOL, read during preparation and stored on the plan, and wraps only the shortfall; the order's collateral amount is unchanged. If the orders do not fit with wrapping, only that owner-to-own-WSOL transfer and its SyncNative move into the wallet preparation transaction. Escrow setup, collateral transfers and all orders remain in the final transaction. A confirmed preparation followed by a rejected or failed order leaves the wrapped amount as wallet WSOL, which the next build spends instead of wrapping again. The sender reports the lamports its confirmed transactions wrapped, and because the TradeBox checks a native SOL payment against lamports only, after such a failure it sets Pay to WSOL and keeps the amount. Before signing a wrapping transaction and again before broadcasting it, the sender requires the live WSOL amount to equal the snapshot; a change or failed read requires a rebuild. Before each signature, the wallet's simulated balance after that transaction must still pay every later transaction's network fee, keeper fees, wrapping and the rent of each account it may create, and leave the wallet rent exempt. A simulation that fails because the wallet cannot pay a fee or rent, or because a System program transfer runs out of lamports, reports insufficient SOL, both before signing and in the signed transaction's simulation; any other simulation failure keeps its raw error. Rent comes from `getMinimumBalanceForRentExemption` and fees from `getFeeForMessage`, both cached for the session; `solReserve.ts` holds the arithmetic. Before any plan is built, the TradeBox's Max and margin slider for native SOL keep back the same reserve, with no extra buffer, for an increase and its TP/SL, counting every account it may create and the highest compute fee the validator accepts for each transaction.

The installed high-level create API generates a fresh random 32-byte nonce internally and fixes the keeper fee at 300,000 lamports per order. The validator decodes each nonce and derives the expected order PDA. Explicit caller nonces and configurable execution fees are not supported by this package interface. A limit order's direction-specific unlimited acceptable-price sentinel becomes the ABI's `None`; market orders require a finite bound. Clearing an existing price to unlimited during update is rejected because this ABI cannot express clearing separately from leaving unchanged. Minimum output uses raw token units for increases and application USD for decreases.

## Signature and send boundary

`prepareGmsolOrderTransactions` snapshots the requested action before awaiting RPC so caller mutations cannot change the order being prepared. It loads the configured active LUT accounts, requiring either no authority (frozen) or an explicitly reviewed GMX authority in `GMSOL_LOOKUP_TABLE_AUTHORITIES` and obtains a confirmed blockhash from the GMX-configured RPC. A frozen table can never change again, so once a read shows it without an authority, its contents are cached for the session; a table with an authority is read every time, so the sender's recheck reads only those. `sendGmsolOrderTransactions` snapshots the plan, rechecks LUT contents, validates every decoded instruction and account, simulates each actual transaction with the wallet's resulting SOL balance, and estimates its network fee before asking the wallet to sign. A read can reach a node that is behind, so the blockhash fetched for a later group requires the slot of the plan's last confirmed transaction as `minContextSlot`, and the pre-signature fee, simulation and block-height reads require the later of that slot and the one the blockhash came from; a node that has not reached it refuses the read, which is retried a few times 500 ms apart. Only the configured gmsol instruction subset, bounded compute-budget instructions, idempotent ATA creation, exact SOL wrapping transfers and wallet SyncNative are permitted. Unknown instructions, extra accounts and unresolved LUT indices fail closed.

The Privy Solana `useSignTransaction` bridge signs bytes without sending. The sender verifies the owner's Ed25519 signature and an unchanged message, or strictly additive Lighthouse account/token assertions. For changed messages, the original instructions, accounts and permissions, compute budget, blockhash and LUT descriptors must remain unchanged; only the read-only Lighthouse program may be added. Assertion payloads are fully decoded against `Jac0xb/lighthouse` ABI `4c579479` (`AssertAccountInfoMulti` / `AssertTokenAccountMulti`); all other instruction kinds, including memory writes/closes, are rejected. The final signed transaction must fit the packet limit and pass signature-verifying RPC simulation before broadcast. The TradeBox and the order actions share one module-level submitter, so only one flow prompts the wallet at a time, and a flow it refuses returns before it shows a toast or opens the wallet. A wallet prompt left unanswered for 120 seconds ends the flow with `GmsolWalletPromptTimeoutError` and frees the submitter; a signature given later is ignored because the flow has already ended, and its blockhash has expired by then anyway. Each click reads the pending record itself, so an unresolved record turns the click into a check of that record and a record that is gone never opens the wallet. Signing and sending eligibility follow the session token from `lib/solana/activeSession`, which changes with the owner or the network and not with the mounted component: a TradeBox remount or a route change keeps a pending preparation or wallet prompt, while an owner or network change ends the flow, even if it is switched back, and frees the submitter. An action submitted while an unresolved record exists throws `GmsolPendingSubmissionError` instead of returning the earlier transaction. The session, block height and freshly fetched `solanaTrading` flag are checked again before each transaction's first broadcast, including after a slow wallet prompt. GMX RPC performs preflight, send and confirmed-status polling. The first send runs preflight with no RPC retries. Once the RPC accepts it, the sender resends the same signed bytes every 2 seconds with preflight skipped and no RPC retries, until a status poll sees a status, the blockhash provably expires, the 90-second wait ends or the flow ends. A resend keeps the signature, so at most one copy lands; its result and errors are ignored, and it never ends the flow or touches the pending record. Confirmation refreshes the shared balances, orders and positions caches, with the confirmation slot supplied to the API; the next wallet prompt of the same action does not wait for that refresh. The highest confirmation-slot floor is retained per API host, wallet and account request even if that refresh fails. Subsequent polling supplies the floor and rejects older responses; the last valid data remains under an error until a qualifying snapshot arrives. The exception is an index that is catching up: for up to 60 seconds after the floor rises, gmx-api's 503 `SLOT_NOT_REACHED` and 429 `BUSY` answers keep the last valid data without an error, and the request stays syncing. Later answers like these, and every other failure, are errors. A read already in flight when the floor rises keeps the last accepted data and reports nothing, because the read made for the new floor decides the state; it is still an error if it answers below the floor it supplied itself. Refresh errors are returned separately from confirmed chain success.

`GmsolTransactionError` retains accepted RPC signatures and a potentially broadcast `pendingSignature`, even when the send request itself times out. Consumers must reconcile those signatures before offering a fresh order retry. A definitive RPC preflight rejection of the first send clears only the matching submission's pending record and omits its `pendingSignature`, allowing a new submission. A rejected resend, even with a preflight error, leaves the record in place, because an earlier copy may already have landed. A timeout or later transaction failure does not roll back earlier confirmed preparation. Apart from resending the same signed bytes, the adapter does not automatically resend, re-sign or rebuild an ambiguous financial action.

## Pending submission recovery

Before broadcasting signed bytes, the sender persists their signature, affected order accounts, operation and last valid block height under the Solana network and wallet owner; a later transaction of a plan also persists the signatures of the plan's confirmed preparation and the lamports it wrapped. A failed storage write prevents broadcast. Repeating an action first reconciles that signature against confirmed/finalized RPC history. A processed receipt, a timeout, an RPC error or a stored field that does not parse remains unresolved and blocks another submission. A missing receipt counts as expired, with nothing executed, only once the finalized block height has passed the last valid block height and the RPC still has no status at or after that finalized slot; the record is then cleared. The send loop applies the same check while it polls for 90 seconds, and a failed status poll counts as a missing receipt until then. A record stored without a last valid block height is cleared once the RPC has no status for it. When a record with a confirmed preparation expires or fails, the check reports that preparation, with any SOL it wrapped now WSOL, instead of nothing executed. A confirmed failed transaction or confirmed preparation step requires a separate, deliberate retry. A confirmed order returns the original signature, refreshes accounts and never signs a replacement. Wallet/network/unmount changes preserve the checkpoint until its owner acknowledges the result. This is a per-owner checkpoint, not an atomic lock between browser tabs.

## Historical finite-bound atomic size baseline (2026-11-13)

Pinned WASM and the two configured mainnet LUT snapshots at slot **468884236** reproduce **1255 bytes** for a BTC/USDC long limit increase plus TP and SL, all with finite acceptable prices. The increase has USD size 10, collateral amount 1,000,000, acceptable/trigger prices 10,000/10,000; TP uses 119,000/120,000 and SL 4,900/5,000. This is an unsigned encoding diagnostic, not a valid market-price recommendation or production signing approval.

After existing deduplication, the message has one `prepare_user`, one `prepare_position`, four different ATA preparations and three `create_order_v2` instructions. The three order payloads are each 131 bytes. There are 13 static accounts and six looked-up accounts across two descriptors. Wire accounting is: signature vector 65 + version/header 4 + static-account vector 417 + blockhash 32 + instruction vector 662 + lookup vector 75 = **1255**. There is no remaining identical preparation to remove.

Reordering the current tables stays at 1255 bytes. Recompiling with only the first table produces 1252; using only the second produces 1376. Neither fits. A diagnostic single-table union of the same address contents produces **1221** bytes by removing one 34-byte lookup descriptor; it preserves all order instructions and price bounds. This union is hypothetical and has not been deployed or approved. Before the compact encoding fix, a reviewed consolidated table was another possible way to address this example's size alongside LUT trust. Its actual contents, authority, activation and coverage must still be checked before use. The production table configuration and signing gate remain unchanged; other markets and parameter combinations need their own size checks.

## Finite-bound atomic encoding fix (2026-11-15)

The atomic recompilation path now encodes a zero `min_output` as `None` instead of `Some(0)` for direct position orders only. At the pinned Rust revision, `init_increase` and `init_decrease` both normalize `None` to zero. The existing ABI reader locates the field; positive minimum outputs, finite trigger and acceptable prices, account preparation and all other instruction bytes remain unchanged. Swap kinds are excluded, and the final transaction still passes the instruction validator and the 1232-byte limit.

With the same real WASM and historical LUT snapshots at slot **468884236**, the finite-bound BTC/USDC limit increase plus TP and SL above shrinks from **1255 to 1204 bytes**. This saves 48 payload bytes and three instruction-length bytes without changing the SDK artifact, price protection or atomicity. Real-WASM regression cases cover both sides, the three supported trigger kinds, zero and positive minimum outputs, and rejection when a positive requested bound is omitted.

An unsigned mainnet simulation with fresh LUT snapshots at slot **469599276** then succeeded at slot **469599277**: `err=null`, 220,099 compute units and three returned 2472-byte order accounts. Signature verification was disabled and no transaction was signed or broadcast. Both tables still retained an authority, so the production trust gate continued to reject them. This resolves the historical packet-size example; it does not establish trusted LUTs, wallet-extension signing, signed landing or keeper execution. Other market and order combinations remain subject to validation and the same packet limit.
