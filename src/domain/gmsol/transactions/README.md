# Solana order transactions

FESOL-56 provides a lazy Solana adapter for shared order-entry and order-editor consumers (FESOL-19). The application and GMX SDK keep their existing USD/token units; `orderInputs.ts` converts them using the FESOL-92 helpers. It does not add another trading page.

## Supported contract

The builder uses GMX-built `@gmsol-labs/gmsol-sdk@0.11.0-beta.1` from `vendor/gmsol-sdk`, with the WASM hash pinned in `config/gmsol/sdk.ts`. The instruction subset in `orderAbi.json` has matching discriminators and account order in `crates/programs/idls/gmsol_store.json` at the pinned source commit `7fe4008292ffc09061f3a733ad9b5cd2e6235fa8`. See `vendor/gmsol-sdk/BUILD.md` for build provenance. Live deployment compatibility still requires simulation and acceptance; a matching package API is not deployment evidence.

Supported actions are direct market/limit increases, market decreases, take-profit/stop-loss decreases, updates and cancellations. Preparation of the wallet user, position and associated token accounts is idempotent. Native SOL payments explicitly wrap only the intended amount into the wallet's WSOL account. Owner, fee payer, receiver and rent receiver must be the connected wallet. Callback orders, swap routes and Token-2022 account setup are rejected until their account ABI is reviewed.

A standalone create has one order. An atomic action starts with one increase and contains at most one TP and one SL for the same position, each no larger than the increase. A WASM transaction group is **not** atomic: the adapter recompiles preparation and orders into one version-0 transaction or fails without sending anything. The packet limit is 1232 bytes; compute units are capped at 1,400,000. Nonatomic preparation/actions execute serially, with at most four transactions total. All transactions share a fresh blockhash and its last valid block height; expiry requires rebuilding and signing again.

The installed high-level create API generates a fresh random 32-byte nonce internally and fixes the keeper fee at 300,000 lamports per order. The validator decodes each nonce and derives the expected order PDA. Explicit caller nonces and configurable execution fees are not supported by this package interface. A limit order's direction-specific unlimited acceptable-price sentinel becomes the ABI's `None`; market orders require a finite bound. Clearing an existing price to unlimited during update is rejected because this ABI cannot express clearing separately from leaving unchanged. Minimum output uses raw token units for increases and application USD for decreases.

## Signature and send boundary

`prepareGmsolOrderTransactions` snapshots the requested action before awaiting RPC so caller mutations cannot change the order being prepared. It loads the configured active LUT accounts, requiring either no authority (frozen) or an explicitly reviewed GMX authority in `GMSOL_LOOKUP_TABLE_AUTHORITIES` and obtains a confirmed blockhash from the GMX-configured RPC. `sendGmsolOrderTransactions` snapshots the plan, rechecks LUT contents, validates every decoded instruction and account, simulates each actual transaction with the wallet's resulting SOL balance, and estimates its network fee before asking the wallet to sign. Only the configured gmsol instruction subset, bounded compute-budget instructions, idempotent ATA creation, exact SOL wrapping transfers and wallet SyncNative are permitted. Unknown instructions, extra accounts and unresolved LUT indices fail closed.

The Privy Solana `useSignTransaction` bridge signs bytes without sending. The sender verifies that the returned message is unchanged and its Ed25519 signature belongs to the owner. An unmounted order flow loses signing/sending eligibility, including when preparation or a wallet prompt is still pending. The session, block height and freshly fetched `solanaTrading` flag are checked again before every broadcast, including after a slow wallet prompt. GMX RPC performs preflight, send and confirmed-status polling. Confirmation refreshes the shared balances, orders and positions caches, with the confirmation slot supplied to the API. The highest confirmation-slot floor is retained per API host, wallet and account request even if that refresh fails. Subsequent polling supplies the floor and rejects older responses; the last valid data remains under an error until a qualifying snapshot arrives. Refresh errors are returned separately from confirmed chain success.

`GmsolTransactionError` retains accepted RPC signatures and a potentially broadcast `pendingSignature`, even when the send request itself times out. Consumers must reconcile those signatures before offering a fresh order retry. A timeout or later transaction failure does not roll back earlier confirmed preparation. The adapter does not automatically resend or rebuild an ambiguous financial action.

## Acceptance and remaining work

`orderTransactions.spec.ts` uses the pinned real WASM, codecs, PDA derivation and Ed25519 signatures. RPC responses are controlled for adversarial preflight/send tests. Those tests do not establish wallet-extension compatibility, live program execution or keeper behavior.

Read-only diagnostics on 2026-11-13 also exercised the GMX-built `0.11.0-beta.1` WASM with SHA-256 `e82184caacc60828f024743f88a0a92d97b9d3d55db6839e0d3fab8a9b46c840`, using the user-selected Phantom public account and actual Mainnet LUT snapshots. Native-SOL limit creation (891 bytes, slot 468836637), create+update (981 bytes, same slot), create+cancel (953 bytes, slot 468836638) and create+update+cancel (1043 bytes, slot 468836639) all simulated successfully. The returned 2472-byte order contained the expected USD 10 or USD 20 size at the pinned ABI offset; cancelled orders returned empty System Program accounts with zero lamports.

BTC/USDC limit creation and the same increase with one or two TP/SL triggers simulated successfully with explicit unlimited decrease acceptable-price bounds: 807, 1044 and 1221 bytes respectively (slots 468836640–468836641). A finite-bound three-order example still required 1255 bytes and was rejected by the builder. A separate unsigned missing-account diagnostic first verified that a random temporary owner/user/position did not exist, then simulated native-SOL order preparation with diagnostic-only funding from the selected account. It succeeded at slot 468836643 (1004 bytes), returning protocol-owned user and position accounts of 520 and 680 bytes. No private key was persisted and the production transfer allowlist was unchanged.

All these diagnostics disabled signature verification and used mutable LUT snapshots only to check program compatibility. At slot 468836635 both configured tables still retained an authority and the production decoder rejected them. No transaction was signed or broadcast; these results do not establish trusted production LUTs, wallet-extension signing, separately landed transactions, indexing or keeper execution.

The following historical read-only mainnet diagnostics used the previous `0.9.0-test.2` WASM. Their results remain evidence for that artifact only; the separate newer-build diagnostics above do not reattribute these historical runs. On 2026-11-13 they used the connected Phantom public account and snapshots of the current LUTs, with signature verification disabled and no signing or broadcasting. A BTC/USDC limit increase simulated successfully (807 bytes, estimated network fee 45,000 lamports). Increase plus TP (1044 bytes, 55,000 lamports) and increase plus TP/SL (1221 bytes, 65,000 lamports) also simulated successfully when the decrease acceptable-price bounds were explicitly unlimited. The last simulation slot was 468611155. These diagnostics establish execution of that instruction subset against the live program; they do not satisfy the production LUT trust gate or prove keeper execution.

Additional unsigned compound simulations created a temporary order and then updated or cancelled it within one simulated transaction. Create+update (897 bytes) succeeded at slot 468614384 and the returned 2472-byte order account contained the expected updated size of USD 20 × 10^20 at the pinned ABI field offset. Create+cancel (869 bytes, slot 468614384) and create+update+cancel (959 bytes, slot 468614385) succeeded and returned a System Program account with zero lamports and empty data. These checks cover fresh-order update/cancel execution without persisting any chain state; they do not establish separately landed transactions or API indexing.

Missing-account preparation was also simulated on mainnet at slot 468617037. A temporary random owner, its user PDA and its position PDA were all absent beforehand. The production builder's validated native-SOL limit order was combined with a diagnostic-only funding instruction from the connected wallet, with signatures disabled. The 1004-byte transaction succeeded and returned protocol-owned user (520 bytes) and position (680 bytes) accounts. No funding instruction was added to the production allowlist, no temporary private key was persisted, and no transaction was signed or broadcast.

With finite acceptable-price bounds on both decrease orders, the same three-order example required 1255 bytes and was rejected. A fresh read at slot 468760972 reproduced this with 13 static accounts, one position preparation and three create instructions. The checked fixed addresses (store, market token, index token, collateral tokens, market PDA, event authority and store wallet) were already in the configured tables. Copying or freezing those same tables therefore does not itself solve this size limit. The builder never removes a user's finite bound, splits an atomic request or submits part of it to make it fit.

- TODO(FESOL-56): resolve or explicitly agree the supported scope of finite-bound atomic combinations exceeding 1232 bytes. First assess a pinned SDK/ABI encoding improvement or a verified account-layout optimization. Do not weaken price protection or assume LUT ownership changes fix packet size.
- TODO(FESOL-56): once trusted LUTs and configured wallets are ready, reconfirm network, deployed ABI/WASM pin, selected account, fresh trading flag, balances, fee budget and wallet authorization. Use a tiny far-from-market limit order; sign, send and confirm creation, then edit and cancel it as separate transactions. Check order state and rent return. Repeat the actual LUT signing/landing check for Phantom, Solflare, OKX and TokenPocket, and verify a supported atomic increase+TP+SL combination. Record transaction signatures, slots, table identities, wallet/version and decoded outcomes; reconcile any pending signature before retry. Unsigned simulation is not a substitute for this acceptance.
- TODO(FESOL-56): retain negative checks for unexpected gmsol instructions, changed owner/receiver/message and unknown LUT authorities before any real signature. Never submit the malicious variants.

The current issue does not require caller-selected nonces, configurable keeper fees, callbacks, routed swaps or Token-2022. These are explicit pinned-interface limits, not additional unfinished requirements. Enabling them later requires a reviewed ABI and, where necessary, an upgraded and repinned external SDK.

Shared order-page integration (FESOL-19), indexed status/notifications (FESOL-20), action UI (FESOL-59) and math rollout (FESOL-112) belong to their own tasks. Keeper execution is a separate integration check from FESOL-56's explicit wallet-signing and transaction-landing acceptance. These boundaries must not be counted as missing adapter implementation or hidden behind a fabricated UI success.
